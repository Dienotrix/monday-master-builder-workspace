# Lean intake skills: notes (call-intake and build-readiness)

Written 2026-10-22 while writing the lean `call-intake` and `build-readiness` skills, so that a demo can start from a raw transcript instead of a hand-made `readiness.md`. Internal build file. Read from: the two lean skills already written, AMENDMENTS (A5, A15, A16, A19, A25, A27, A28, A31 to A37), BUILD-PLAN WP8 and WP19, `stage-1b/build-readiness-spec.md`, ARCHITECTURE A§3.0 to A§3.3, A§6, A§8.3 and A§8.4, the record map, the record templates and `record.py`'s parser and commands. No fixture, answer key or client record was read.

Each note says what was open or missing, and what the skills took. The ones that matter most for a demo come first.

## A. Gaps in the record map, the templates and the scripts

1. **The call summary's body is not pinned.** The record map pins a call summary's front matter (the six type-header fields and the call-set fields), the client-safe marks and the `## Conflicts` heading, and nothing else. There is no `call-summary.md` or `document-summary.md` template either, though the record map's file table names the second. Took: the shape is written in `call-intake/references/intake-shapes.md` (front matter, then `## Call type`, `## Speakers`, `## Goals`, `## Pains`, `## Signals`, `## Entities`, `## Current tools`, `## Figures`, `## Open questions`, `## Commitments`, `## What the input cannot see`, `## Conflicts` when there is one, and the client-safe block). The headings for goals, pains, signals and entities match the readiness headings, so the readiness check can lift them across. Should follow: the two templates in WP7, and the record map's pin.
2. **The exclusions template and the leak lint disagree.** `templates/record/exclusions.md` carries a table (what must not appear, who said it, where, added). The lint reads only `- term [kind: ...; added: ...; by: ...; source: ...]` rows under a level-2 heading that reads exactly `## Exclusions`, so a row written in the template's table is silently ignored, and the blueprint's sample data could then carry it. Took: both skills write rows in the lint's form under `## Exclusions`, a heading added after the template's table (the strict reader refuses any non-row line under the heading, so the table cannot sit below it). Should follow: the template carries the `## Exclusions` heading and no table.
3. **No intake scripts.** `transcript_measure.py` and `transcript_prep.py` wait under A31, so there is no measuring, no intake report, no `type` proposal and no `verify-quotes`. Took: the session reads the saved file itself, in chunks, and verifies every quote by searching the saved raw file for the exact words and checking the speaker label above them. The skill names no script that does not exist, since the plugin lint fails on a `${CLAUDE_PLUGIN_ROOT}` path that does not resolve.
4. **No `meetings.md` template and no pinned body.** The record map gives `meetings/1` (one line per meeting, a package block, a who-has-seen-what block) and no line shape. Took: a minimal shape in the reference (`## Meetings`, newest first, one line per call; `## Packages` when a package arrives). The who-has-seen-what block is left out of the lean version.
5. **The readiness Markdown headings are not pinned, except `## Assumptions`.** The record map says `readiness.md` carries the parts "in this order, under the same names" as `readiness/1`, and `record.py` reads only `## Assumptions` and its line form. Took: one level-2 heading per field, in the pinned order: `## Note`, `## Goals`, `## Pains`, `## Signals`, `## Entities`, `## Structure` (with `### Leanings`, `### Patterns`, `### Element per pain`), `## Existing`, `## Assumptions`, `## Unmet needs`, `## AI opportunities`, `## Verdict`, `## Questions`. `cleared_for` sits under `## Verdict`, where the record map says solution-blueprint reads it. Should follow: the pin, when build-readiness's script embeds the tokens.
6. **"The seven sweep patterns" are named nowhere I may read.** `structure.leanings[].pattern` is "one of the seven sweep patterns, in prose, or `fork`", and neither the record map nor the design documents list them (they may live in the fixture review). Took: the skill asks for the pattern named in a few words, `parent-row-with-roll-up` where children move on their own, or `fork` for two client speakers who disagree. Should follow: the seven listed in the record map.
7. **The type-header state word.** The record map pins `detected`, `proposed` and `confirmed`; ARCHITECTURE A§6 and A27 say `assumed`. Took: the pinned `proposed` in the front matter (the lint asserts the pinned tokens against `transcript_prep.py` once it exists), with the skill saying that it means assumed: intake carries on with it and tells the user. A§8.3 also spells `nobody-shows` and `yes`/`no` for `money_live`, against the record map's `no-show` and `not-live`/`live-approver-present`/`live-approver-absent`; the record map is followed.
8. **The flat front matter cannot carry the header's signals or candidates.** Took: the six fields as `"<value> <state>"` (or `"unresolved"`), and the signals, candidates and fallback in the body under `## Call type`.
9. **A call's file stem carries its type, and a raw file is never renamed.** `add-transcript --type` names the file, so the type has to be guessed before the save, and a later correction changes `call_type` in the summary but not the stem the transcript and the summary share. Took: guess first, then save; a correction is written into the summary and logged, and the stem stays. Worth a nod: whether a correction should ever re-save.
10. **The STRAND.md template has no "what this build rests on" block.** ARCHITECTURE A§8.4 has build-readiness update it. Took: the lean skill sets `clearance`, `stage` and `next_step` and writes `## Next step`, and leaves the block out; the assumptions live in `readiness.md`, which the card reads.
11. **No `open-questions.md` template.** A§8.4 has the readiness check insert its questions and every conflict there. Took: the lean skills keep conflicts under the summary's `## Conflicts` and the questions in `readiness.md`, as the lean blueprint writes no `open-questions.md` either.
12. **`record.py init` has no `--record` in the ordinary case.** With `--record` the folder's name must equal the slug; without it, the record goes to the home's `clients/<slug>/`. Took: the skill gives the form without `--record`.

## B. Choices the design left open, and what the skills take

13. **When the call date is missing.** A§8.3 says ask only for what is missing; A27 says ask only what cannot be inferred. Took: the date the input or the user gives; otherwise today's date for the stem, `call_date: "unknown"` in the summary, and one line to the user. A demo is not held up for a date.
14. **A summary log entry.** The save entry is written by `add-transcript` at record level. Took: one more `call`, `document` or `email` entry at the strand's position, keyed by the stem, whose body has no `path:` line, so `record.py check` never reads it as a second save.
15. **Current tools as categories.** Took: a spreadsheet, a shared calendar, an accounting package, paper, email, and so on, with what each holds and what it stays the system of record for. The readiness check's authority table and the blueprint need what the tool does, not its brand, and a category never travels into monday as a product name.
16. **The leak lint at intake.** Took: `leak_lint.py scan` over the new summary, which checks only its client-safe block. A block is fixed by rewording. If the lint cannot run (no settings), intake says so and carries on, since nothing leaves the record at intake in v1; the payload check at every write still guards monday.
17. **The A11-3 stop.** Kept as the design has it: a real input is not saved while either field is `unanswered`; the skill asks the one three-part question and records the user's answer, and never picks one. A fictional input is saved with `--fixture` only on the user's word that it is fictional.
18. **Which strand.** One strand is opened at `init`. When two are open and the input does not say which it serves, intake asks; otherwise it uses `current_strand`.
19. **Strand kind.** `platform` unless the input asks only for work outside monday (`non-platform`) or for both (`hybrid`), with the reason in `--reason`; the call's `output_class` guess feeds it.
20. **build-readiness and the keep-out lines.** The blueprint skill compares "what must stay out" with `exclusions.md`. Took: the readiness check adds any missing row itself, through the guard, citing the client's words, so the gap is closed before the blueprint starts.
21. **`products_in_scope`.** Took: build-readiness sets it in `CLIENT.md` through the guard (Work Management is `core`) when the products it names differ.
22. **The readiness log key.** Took: the clearance string, which is one line with no ` · `.
23. **Chaining.** call-intake chains build-readiness without asking (record-only, A§3.0), once per package. build-readiness chains solution-blueprint when the clearance is `cleared to build` or `cleared to build, generic` and the user asked for a demo or a build; on `not yet` it shows the questions and stops.
24. **Workspace names in readiness.** `<client> – Ops` for Work Management, `<client> – CRM`, `<client> – Service`, as A21 and the record map's example have them; solution-blueprint already maps them to the test workspace while the plugin is developed. A CRM or Service build adds the condition that a workspace in that product is needed (A5, A37), without naming the test workspace.
25. **AI opportunities' probe basis.** From A§9.4: P-19 for an agent, P-20 for a Vibe app, P-21 for a workflow; an AI column and a sequence are `unprobed`.

## C. Not settled

26. **The full skills' size.** The lean skills are about a hundred lines each against WP8 and WP19's 190, and leave out: the alias table, composite blocks and wedges, the package's set script, the structure inventory for a reverse demo or a document's diagram, the backlog's Incoming seeds, the reactions after a shown version, the stakeholders block of `CLIENT.md`, `open-questions.md` and the scoping route's `scope` entry. The scoping route is one line in call-intake (it tells the user and leaves the strand kind to them).
27. **Not tested on a real input yet.** The skills have been linted, and their command forms dry-run, but not run on a transcript by a fresh agent. The first demo through them is the test, as with demo 2.
28. **The dry run (scratch home, fictional values, deleted afterwards).** `home init`, `init`, `add-transcript --fixture`, the second save refused as already saved and for the open A11-3 fields, `guard` on a new `calls/<stem>.md`, on `exclusions.md` with the `## Exclusions` heading after the table, on a new `meetings.md`, on `readiness.md` and on `STRAND.md`, `log` at the strand and at `-`, `leak_lint.py scan` on the summary (mode `client-safe-block`, clean), `record.py check` (clean), and the strand index picking up the clearance. A payload carrying the excluded name was blocked by the `exclusion` rule, so note 2's form works.
29. **Reference file names.** WP8 names the intake reference `summary-and-recap.md` and WP19 names `readiness-guide.md`. The second is used. The first is `intake-shapes.md`, because this session's tooling refused to write a file with "summary" in its name; the full skill can rename it.
