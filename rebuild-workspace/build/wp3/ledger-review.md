# WP3 `ledger.py` write path: adversarial review

Date: 2026-10-16. Internal build file: never client-facing. No code was changed.

Scope: the write path of `plugins/monday-master-builder/scripts/ledger.py` (the frame, `Ledger`, `fenced`, `fence`, `commit`, and the subcommands `run start`, `run heartbeat`, `run end`, `intent`, `record`, `verify`, `depart`, `irreversible-yes`, `ui-step`, `approval`, `change-check`, `bind`, `workspaces`, `native-map`, `live-map`, `live-map set`, `reconcile`, `estimate --write`) and its use of the lease primitives and the record mutex in `mmb_common.py`, read against PLAN step 7, DECISIONS section 1 (W44 answered `per-list`), W06 to W72 and W92, both parts of `API-ledger.md` with their choices worth the user's nod, and the contract clauses the code claims for each.

Method: each finding marked "proved" was shown by a throwaway probe run with `PYTHONDONTWRITEBYTECODE=1` under `py -3.14` on a copy of the unit fixture outside the repository (`scratchpad\ledger-review\`, probes P1 to P21; temporary, not kept). The probes subclass the suite's own `Base` from `test_ledger.py`, imported read-only, so each copies `tests/unit/fixtures/home/` into `scratchpad\ledger-review\tmp\`, points `MMB_HOME` there and `HOME`/`USERPROFILE` at an empty canary, and pins the clock; `Base` asserts the fixture tree unchanged at the end. Windows failures were simulated with the suite's `failing()` patch, which makes `mmb_common.write_file` raise the `OSError` a sharing violation gives. Line numbers are as of this review.

Severity: **blocking** (fix before WP3 is accepted), **should fix**, **note**.

## Findings

### 1. The approval mode is read from the revision that planned the row, so a working solution rides the proof of concept's card (blocking)

- Where: `ledger.py:1818` (`ref = args.approval_ref or row.get("approval_ref")`), `:2045` (`mode = (entry or {}).get("approval_mode")`), `:2090` (the `card` entry); `:1465` (`approval` keeps a kept row's `approval_ref` as it was).
- Scenario: the user's own account. v0.2 is a proof of concept, approved `own-account-poc`; it builds automation `A1` and workspace `W2`. v1.0 is the working solution, approved `per-list` as the user decided for W44. A kept row keeps the ref of the revision that planned it (`v0.2r1`), and `intent` takes the mode from that entry. So in the v1.0 run, `intent A1 --operation update` (a list row: a `grouped` yes in this run under `per-list`) and `intent W2 --operation archive` (class `removed`: a `per-item` yes with evidence under `per-list`) both pass with no yes, and `intent` writes a `card` entry for each. The same happens without any edit when the session passes `--approval-ref v0.2r1` for a row of the current table: any approval of the ledger whose table holds the key lends its mode.
- Proved: yes (P1: v1.0 approval `per-list`, `A1` kept; `intent A1 --operation update` exit 0, `approval_mode own-account-poc`, `yes card`; `intent W2 --operation archive --evidence ...` exit 0, class `removed`, `yes card`).
- Breaks: W44 as the user answered it (a working solution in the user's own account takes each list's own yes and the execution-time confirmation), W10's `per-list` column, A28 (the one yes is for a proof of concept only).
- Smallest fix: take the mode for the yes from the approval of the version being built (`version.md`'s revision, the entry `run start` checked), never from the row's planning ref; keep the row's ref only for the table match (key, kind, name). Refuse `--approval-ref` naming an entry of another version than the strand's current one, except for the archive or change of a kept row, which then takes the current version's mode. A test: v0.2 POC, v1.0 working solution, update and archive of a v0.2 row both need their own yes.

### 2. One per-item yes covers every later irreversible step on the same key in the run, an archive included (blocking)

- Where: `ledger.py:2046-2050` (the yes is matched by key, mode and time only), `:2055-2058` (the archive's evidence may come from `--evidence` instead of the yes).
- Scenario: a client-account record (`per-list`). The user says yes to "create workspace W2" (`irreversible-yes --key W2 --mode per-item`). The session creates, records and verifies W2, then intends `--operation archive` on it in the same run with `--evidence "nothing uses it"`. The archive is class `removed`, which needs its own `per-item` yes with containment evidence (W10, A§9.4:880); the create's yes satisfies the match, and the evidence comes from the flag, so the archive passes without the user ever being asked about it. The same covers an `update` of a verified workspace, folder or subitems row, or a `convert` after a `create`, on the first yes.
- Proved: yes (P2: one entry, `what` "the step for W2", given for the create; `intent W2 --operation archive --evidence ...` exit 0, class `removed`, `yes per-item`).
- Breaks: A§8.6:800 (each irreversible step its own yes at execution), W10 (`removed`: a `per-item` yes with containment evidence), W48 (the archive's evidence on its yes), K215.
- Smallest fix: a yes is consumed by the intent it covers: record the yes's `run_id` and the operation it was given for (`irreversible-yes --operation`, defaulting to `create`), match both, and mark the entry used (`used_by: <attempt started_at>`) when `intent` accepts it; an `intent --retry` of the same attempt may reuse it. For `removed`, take the evidence from the yes only.

### 3. A parent named by `--parent-id` alone is never placed and never checked against `do-not-change` (blocking)

- Where: `ledger.py:1886` (`parent_id = args.parent_id or row.get("parent_id")`), `:1887` (only its digits are checked), `:1917-1923` (the `do-not-change` guard reads keys only); the placement of W40 runs on `--ref` values (`:1976-1993`) and never on `parent_id`.
- Scenario: the rows with no parent in their key (a board, a doc, a dashboard, a folder, an automation, a portfolio, a project, a workflow) take `--parent-id` freely. (a) `intent A1 --parent-id 88800000001 --workspace 40000001`: the automation's board is in no workspace the record knows, yet the row goes `attempting` with that `parent_id` and the client's workspace as its `workspace`; the write then lands on whatever board that id is, in any workspace of the account, an operational one included. (b) Board `001:B1` is marked `do-not-change`; `intent A1 --parent-key B1` is refused, but `intent A1 --parent-id 50000001 --workspace 40000001` (the same board, by id) passes.
- Proved: yes (P3: exit 0, row `parent_key null`, `parent_id 88800000001`, `workspace 40000001`, `attempting`; P3b: the key form refused "001:B1 is marked do-not-change", the id form exit 0).
- Breaks: W40 (a board, doc, view or column id a write names is placed only by the record, else refused), W41 and A21 (every reference inside the client's workspaces), K157's third case and choice 21 of `API-ledger.md` (no write whose parent's live row is `do-not-change`).
- Smallest fix: treat `parent_id` as a reference: place it (W40) and require the placed workspace to be the row's `workspace`; resolve it to its row or live row and run the `do-not-change` guard on that (see also finding 5); refuse `--parent-id` without `--parent-key` where the record holds the parent, so the parent is always named by key.

### 4. A workspace id with a leading zero passes the operational list (blocking)

- Where: `ledger.py:503-505` (`digits` accepts any `[0-9]+`), `:1241` and `:1777` (the operational test is a string lookup), `:1222-1240` (`workspaces` stores the id as given).
- Scenario: `local/settings.json` lists workspace `40000002` in `never_show_workspaces`. `workspaces --product crm --id 040000002 ...` records it as the client's crm workspace and a target of the strand (the lookup misses), and `intent B2 --workspace 040000002` then passes the scope check. If monday resolves that `ID` to the number it spells, as numeric parsing would, the board lands in the operational workspace; if it resolves to nothing, the record now names a client workspace that does not exist. Either way the record's ceiling holds an id the operational list was meant to keep out. The control (`--id 40000002`) is refused as it should be. Every other comparison in the scope check is a string comparison too, so the same spelling slips past a sibling's or a superseded id wherever a list is matched.
- Proved: yes (P4: `workspaces --id 040000002` exit 0; `intent B2 --workspace 040000002` exit 0; `--id 40000002` refused "an operational workspace").
- Breaks: W35 ("must match `^[0-9]+$` and is stored as the string given" was meant to keep ids exact, not to admit two spellings of one id), W41 and K65 (an operational id refused by `workspaces` and `intent`), A21.
- Smallest fix: one id rule for every command-line and file id: `^[1-9][0-9]*$` (monday ids never start with 0), refused otherwise, so one id has one spelling and every string comparison is exact. A test: `040000002` refused by `workspaces`, `intent --workspace`, `--scope`, `--ref` and `--parent-id`.

### 5. `do-not-change` is checked by qualified key, so one monday object under two live keys is protected under one only (blocking)

- Where: `ledger.py:1917-1923` (the guard reads `<short>:<key>` and the parent's key), `:1878` (the `other-strand-modified` guard reads its `--live-key`); `live_rows` (`:1613`) gives every strand that verifies a referenced or pre-existing row a live row of its own (W60).
- Scenario: strand 002 references the client's board "Supplier list" and closes; the client said it must not change, so its row `002:B9` is promoted to `do-not-change`. Strand 001's blueprint also references that board as its own `B9` (a `pre-existing-referenced` row, verified with the board's id) and plans a column `B9.C1` on it. `intent B9.C1 --operation create` looks only at `001:B9.C1` and `001:B9`, finds neither protected, and passes; the column is written into a board the live map says nothing may change. Two strands referencing one client or native board is the ordinary case W60 creates, not a planted one.
- Proved: yes (P5: `002:B9` `do-not-change` on monday id `50000099`; 001's `B9` verified with that id; `intent B9.C1 --operation create` exit 0, class `irreversible`, no refusal).
- Breaks: K157 and choice 21 (no write whose own or parent's live row is `do-not-change`), A§7.8 (the constraint protects the object, and a row is the object's mirror), K244 in `check`, which has the same blind spot.
- Smallest fix: run the guard on monday ids: the set of ids of every `live_objects` row marked `do-not-change`, against the row's own id (for an update or archive), its `parent_id` (finding 3) and its referenced ids; `verify` of a referenced row whose id another live row holds should say so and take that row's constraint. `check` should block two live rows with one `monday_id` and different constraints.

### 6. A `run start` whose ledger write fails leaves a lease nothing can end (blocking)

- Where: `ledger.py:1567-1572` (`run start` refreshes the run id into the lock first, then writes `build.json`, W25), `:4014-4016` (`reconcile --classify-only` refuses a lock run id with no run in the ledger), `mmb_common.py:536-552` (`_reconcile`: condition 4 looks for that run in the ledger), `lease_repair` (refuses a sound lock).
- Scenario: on Windows the sync client holds `build.json` for a moment and `run start` fails after the refresh: exit 3, `committed` naming `.work/lock.json`, and `next` the same call with `--run-id`. That retry needs the session's own epoch and label. If the session ends before it retries (closed, crashed, the machine slept), the lock is `held` with a run id that no ledger holds. After the heartbeat goes stale, the classify-only reconcile is refused ("the lock's run ... is no run of strand 001"), so condition 4 can never be met, and `lease break` is refused for resume and for park; `lease repair` refuses because the lock is sound. The record is wedged for every strand until someone edits the lock by hand, which the design forbids. Nothing can have been written under that run: every fenced command checks `--run-id` against the ledger's runs (`run_reasons`) before the fence.
- Proved: yes (P7, with `build.json` failing as a sharing violation would: exit 3, `written` `[.work/lock.json]`, lock run id `run-2026-11-05-1`; three hours later the classify-only reconcile exit 1 as above, `lease_break` resume and park both refused "has no classify-only reconcile after the last heartbeat", `lease_repair` refused "the lock reads and is sound").
- Breaks: W25's promise that the failure leaves a state recovery handles (the table names the `--run-id` retry only), A§8.11 and G04 (a stale lease can always be broken with a reconcile), W72 (a lock run id with no run is refused, with no way forward named).
- Smallest fix: classify-only over a lock run id that the holder's ledger lacks appends that run as `{id, state: "interrupted", reconcile: {...}}` with a note that it never reached the ledger (or `_reconcile` treats such a run as the null-run case, since nothing could be written under it). Also make `next_run_id` skip every run id in the lock's history, so the next `run start` that day does not mint the same id and meet `lease_refresh`'s "ran under the lease of epoch" refusal.

### 7. A classify-only reconcile over an old inventory meets condition 4 (blocking)

- Where: `ledger.py:3688-3704` (`inventory_reasons` checks that `read_at` is a stamp, not when it was taken), `:3982-3988` (with no `--inventory`, the copy left by any earlier reconcile is read), `:4019-4024` (the block's `at` is the time of the call); `mmb_common.py:546-547` (condition 4 compares that `at` with the heartbeat).
- Scenario: the holder's create of board B2 timed out (`attempting`) and its session went quiet. In fact the call landed twice. A reconcile on today's read classes B2 `duplicate`, which forbids a park. The sibling's session instead runs the classify-only form over an inventory read the day before (or, without `--inventory`, over the copy an earlier full reconcile left in `.work/strands/001/`): B2 classes `retry`, the run is marked `interrupted` with a reconcile stamped now, after the heartbeat, and the park break for strand 002 is accepted over a duplicate.
- Proved: yes (P8: today's read gives B2 `duplicate`; the classify-only form on a read with `read_at` `2026-11-04T09:00:00Z`, heartbeat `2026-11-05T14:30:00Z`, exit 0, `duplicate 0`, `retry 1`, marked; `lease_break(..., "park")` accepted).
- Breaks: A§8.11 and G04's condition 4 (the reconcile is a read of the account after the holder's last heartbeat), C107 (no park over duplicate or partial elements), W72 (the classes the break reads are the account's).
- Smallest fix: `reconcile --classify-only` refuses an inventory whose `read_at` is not later than the lock's `heartbeat_at` (and later than every `attempt.started_at` of the run), and stores `read_at` in the `reconcile` block; `_reconcile` compares the block's `read_at`, not its `at`, with the heartbeat. The copy fallback should apply only to a retry of the same call (the `committed` case of W25), for example by refusing a copy older than the lock's heartbeat.

### 8. `workspaces` records any workspace id as the client's, so the A21 ceiling is a claim (blocking)

- Where: `ledger.py:1232-1255` (the `--product` form checks the product, the digits, the operational list, a clash with another product and the one-per-product rule), `:1275-1286` (it then adds the id to `client_workspace_ids`, the strand's targets and `product_workspaces`).
- Scenario: W38's first form "records a workspace the build created". Nothing ties the id to the build: no `workspace` row of the strand with that id and status `written` or `verified` is required, and no other record under the home is read. In the user's own account, where several clients' proof-of-concept records share one monday account, a session on one record runs `workspaces --product crm --id 40000077`, the id of a workspace another client record holds; it becomes this client's crm workspace and a target, and `intent B2 --workspace 40000077` then passes every scope check. The `client_workspace_ids` list is the ceiling every other check rests on (G47, K67), so one unproven call moves the ceiling.
- Proved: yes (P19: the strand's workspace rows are `W1` verified as `40000001` and `W2` planned; a sibling record under the home lists `40000077`; `workspaces --product crm --id 40000077 ...` exit 0; `intent B2 --workspace 40000077` exit 0).
- Breaks: W38 (a workspace the build created, with the product read back at creation), A21 (a new workspace per client and product; the plugin never writes into any other workspace), BP:136 and H58.
- Smallest fix: the `--product` form requires a `workspace` row of this strand whose `id` is `--id`, whose status is `written` or `verified` and whose `product` is `--product` (W11 already stores it), and takes the name from that row; refuse an id that another record under the home lists in its `client_workspace_ids` or `superseded_workspaces` (one read of each `clients/*/account.json`, ids only, under this record's mutex, as `estimate` already reads siblings for totals).

### 9. An `other-strand-modified` row rewrites the owner strand's live row with whatever id was recorded (should fix)

- Where: `ledger.py:2146` (`record --id` sets any id), `:1632-1636` (`run end` copies the row's `id`, `workspace`, `state` and `digest` into the row its `live_key` names).
- Scenario: strand 001 modifies board `003:B7` (monday id `50000077`), built by strand 003. Its row is `other-strand-modified` with `--live-key 003:B7` and a prior state naming `50000077`. `record --id 59999999` (a typo, or the id of the object the call actually touched) is accepted, `verify` matches a read that never states an id, and `run end` writes `monday_id 59999999` into 003's row, keeping 003 as owner and the old `name_at_build`. Strand 003's live row now points at another object, and nothing in the record flags it. The same holds for a `pre-existing-modified` row, whose id nothing compares with its prior state.
- Proved: yes (P6: after 001's `run end`, `live_objects["003:B7"].monday_id` is `59999999`, owner `003`, `name_at_build` "Stock").
- Breaks: W61 (a later run refreshes the row of the object, never makes it another object), W50 (the `live_key` row is the object modified), A§7.8:708 (a strand edits only its own rows; a refresh of another's row must not change what it describes).
- Smallest fix: on an `other-strand-modified` row, `intent` sets `id` to the live row's `monday_id` and `record` refuses another `--id`; on a `pre-existing-modified` row, `record` refuses an id that differs from `prior_state.id` when the prior state carries one. `verify` on either should refuse a read whose `object.id`, when present, differs.

### 10. Nothing refuses a retry, a departure or a new write before the reconcile that a timed-out call or an interrupted run requires (should fix)

- Where: `ledger.py:1747-1752` (`intent --retry` on an `attempting` row needs nothing), `:2151` (`record --timed-out` only says "possibly applied: reconcile before any retry"), `:1573` (`run start`'s `recovery_first` is printed, not enforced), `:2317-2349` (`depart` takes an `attempting` row).
- Scenario: a create times out and is recorded `--timed-out`. In the same run `intent B2 --retry` is accepted at once, which is how the duplicate is made. In a new run after an interrupted one, `run start` says `recovery_first: true`, and still `intent B2 --retry`, an `intent` on a new row and a `depart` of the possibly-applied row (which then stops counting as attempting at `run end`) are all accepted with no reconcile in between.
- Proved: yes (P9: the same-run retry exit 0; after an interrupted run `recovery_first` true, then the retry, a fresh `intent B1.G2` and `depart B2` each exit 0).
- Breaks: A§8.6:798 and :799 (a timeout is reconciled before any retry), W13 (`attempting` to `attempting` "after a timeout, or a reconcile `retry`"), W30 (e) ("the session reconciles before any new write"), A§8.11.
- Smallest fix: `intent --retry` of an `attempting` row requires a reconcile entry classing that key `retry`, written after the row's `attempt.started_at` (the full form can record its plan in the run, or the retry names the reconcile it follows); `run start` with `recovery_first` true records it on the run, and `intent` and `depart` refuse until a reconcile of that run has been recorded. `depart` of an `attempting` row needs the same.

### 14. A recorded account mismatch does not stop the next write (should fix)

- Where: `ledger.py:1595-1611` (`run heartbeat --account-check mismatch` appends the check and prints `stop: true`); no command reads `account_checks[]` afterwards.

The mismatch is recorded and the output says stop, but `intent` for the next write passes the fence and every other check, and the write can go into the other account. - Proved: yes (P20: `run heartbeat --account-check mismatch` gives `stop: true`; the next `intent B2` exit 0, `attempting`).

### 15. A yes "never carries to another run" only while the wall clock never steps back (note)

- Where: `ledger.py:2048-2049` (a yes counts when its `at` is not earlier than the run's `started_at`); an `irreversible_yes` entry carries no run id.
- Scenario: run 1 records a `per-item` yes for `F1`, ends, and the lease is retaken; the system clock is stepped back two minutes (a time-sync correction) and run 2 starts. Run 1's yes is "not earlier" than run 2's start, so `intent F1` in run 2 takes it as its own. Two runs ending and starting within one second give the same result.
- Proved: yes (P12: run 2 started two minutes "before" run 1's yes; `intent F1` exit 0, `yes per-item`).
- Fix: store the run id on each yes (`irreversible-yes` is fenced, so it has it) and match on it; keep the time check as a second test. This also gives finding 2's fix its anchor.

### 16. A superseded workspace can be taken up again as a target (note)

### 17. A referencing strand owns the live row of a client or native object (note)

- Where: `ledger.py:1644-1647` (`run end` gives a `pre-existing-referenced` or `pre-existing-modified` row `owner_strand` the strand, `built by` `client` or `native`), `:1128-1131` (`live-map set` checks `owner_strand` only).

- Proved: yes (P14: `001:B9` built by `client`, owner `001`; `live-map set --strand 001 --key 001:B9 --constraint free` exit 0).
- Fix: one live row per monday id (finding 5); a client or native row's constraint is set only from a client quote or a user decision, the source naming it, whatever the strand.

### 18. Any strand's change check replaces the one block the holder's writes depend on (note)

- Where: `ledger.py:1305-1336` (`change-check` is unfenced and replaces `account.json.change_check` whole), `:2034-2042` (the gate in `intent` needs `for_strand` to be the strand).

### 19. A first write that fails after the fence says "nothing was written" (note)

- Where: `ledger.py:563-566` (`commit`); the fence has already moved the heartbeat in `account.json` and the lock.
- Scenario and proof: P17: `intent` with `build.json` failing exits 3 with "nothing was written", yet `account.json` and `.work/lock.json` changed (the heartbeat moved to 14:34). Harmless to the lease (a moved heartbeat is the holder's own), but the words are not true, and a session reading them as "the call left no trace" may conclude the fence never ran. Related: no `committed` report carries the new sha of a `build.json` it wrote, so the `run end` retry of W25 needs a `check` first for its `--expect-sha`; `next` could say so, or the report could carry `written` with shas.
- Fix: "the ledger write was not made; the fence moved the heartbeat", and `committed.written` as `{path: sha}`.

### 20. Smaller points read and not probed (note)

- **Recipients come only from `intent`.** `approval` records no recipient for any row (the element table is key, kind, name, W42), so the "real person" rule of W45 rests on the session passing `--notifies` at `intent`; an automation intended without it rides the card under `own-account-poc`. A later blueprint column for recipients, or `approval --notifies <key>=<recipient>`, would let the script hold the session to the approved list.
- **Unfenced writers of a live strand's ledger.** `approval`, `ui-step` and `estimate --write` may rewrite a running strand's `build.json` from any session; `--expect-sha` keeps them from clobbering, and the running session's next write is refused on its sha. An `approval` mid-run can move a `departed` row back to `planned` under the run. Refusing `approval` while the strand holds the lease would close that.
- **`commit` catches `OSError` and `MMBError` only** (`ledger.py:560`); any other exception from a later step goes to the generic handler with no `committed` report. No such path was found in the current steps.
- **Classify-only with an unreadable heartbeat** (`fresh: null`) is treated as not fresh (choice 15 of part 2). The primitives refuse such a lock, so it can only come from a hand edit; noted for the record.

## Checked and holding

- **The fence's three parts.** An old epoch, an old label and an old run id are each refused (K104 to K108); a fenced write before `run start` is refused because the lock carries no run id ("no run has started under this lease", K109, WP2 finding 2 as fixed); a run id from an earlier lease cannot enter a new one (`lease_refresh`'s history check, K101); a missing flag is a refusal, never filled from the lock or the ledger (W29, K112). `ledger.py` never writes the lock or `guard_index.lease` itself: every lease change goes through a primitive, and every `account.json` write after a fence comes from a fresh `led.reload()` inside the same hold, so the mirror the fence moved is carried, not rolled back.
- **Every account-affecting subcommand fences first.** `intent`, `record`, `verify`, `depart`, `irreversible-yes`, `run heartbeat`, `run end` and `workspaces` validate, then call `lease_fence`, then reload, then write (W28); `run start` enters its run through `lease_refresh` (G51 amended). No other subcommand writes anything that leads to a monday write. A torn lock gives exit 3 and a malformed one exit 1 on each of them with the record tree unchanged (P18, five commands times two lock states).
- **The record mutex.** `main` takes it once around the command and its `emit` (W25); `lease_fence`, `lease_refresh`, `lease_release` and `lease_status` re-enter it in the one thread (K45); every file read and write sits inside the hold (K41's spy). The only reads before the hold are the two `is_file` tests on `CLIENT.md` and `account.json`, which decide nothing beyond "can run". No read feeds a decision after the hold ends.
- **Post-commit reports.** `run start` (both answers), `run end`, `live-map set` and `reconcile --classify-only --inventory` each report `committed` with `written`, `not_written`, `lease`, `run_id` and `next` on a failure after the first write, and their retries complete without duplicating (K48 to K51 and the W25 retry test; for `run end`, a repeat on an `ended` run rewrites the live rows as equal and releases). `bind`, `workspaces`, `change-check` and `native-map` write `account.json` once. The gap is finding 6 (the run start retry needs the dead session).
- **`--expect-sha`.** Every `build.json` writer but the classify-only reconcile checks the bytes inside the hold before it writes (W34); no primitive writes a `build.json`, so nothing between the check and the write can change it.
- **Ids as numbers and with whitespace.** A JSON number under an id key in any input file is refused (K131); a command-line id with a space, a sign, a newline or a non-ASCII digit fails `[0-9]+` under `fullmatch`. Leading zeros are finding 4.
- **Approval modes at approval time.** `approval_mode` gives `own-account-poc` only for an own-account record on a proof of concept, and `per-list` for a client account, a sandbox and a working solution (W44 as answered, K72); a list row or a card row that notifies anyone but the bound user needs its own yes in either mode (K73); an `approval_ref` resolves only inside the strand's own ledger, so another strand's approval can never be named (W43). The gaps are at `intent` (findings 1, 2, 12, 13).
- **Status transitions and `prior_state`.** Every move outside W13's table is refused (K122); `delete` is refused for every kind; a `pre-existing-referenced` row never passes through `intent`; `prior_state` is required on the two modified origins and refused elsewhere (K127, K128); an `other-strand-modified` row needs a source strand that is not its own and a live row of that strand that is not `do-not-change` (K129, K130). `live-map set` refuses a row another strand owns (W62).
- **`reconcile --classify-only`.** It writes only the holder's run (`state` and `reconcile`) and `updated_at`: no row is adopted, retried, departed or archived, and `account.json` is untouched (P21); it refuses while the holder is fresh (P21) and while another strand holds the lease. The gaps in when its object should satisfy condition 4 are findings 6 and 7.

## What the Windows and macOS runs must exercise

- **A real sharing violation at each multi-file step** (findings 6 and 19): another process holding `build.json` open without sharing (on Windows a `FileShare.None` open from a second process, or the sync client; on macOS a held `fcntl` lock or an iCloud or Dropbox write) during `run start`, `run end` (at each of its four writes), `live-map set` and `reconcile --classify-only --inventory`, with the `committed` report and the retry checked on disk. The unit tests only patch `write_file`.
- **A write torn mid-file.** `write_file` truncates and rewrites in place (C14, C15); a failure after the truncation (a full disk, an on-access scanner) leaves a half-written `build.json` or `account.json`. Only a real file system shows whether the `.work/backup/` copy and `check` then lead the user back.
- **Two sessions, two processes.** A holder that stalls past 60 minutes and a sibling that runs the classify-only reconcile and the break (findings 6 and 7), and a woken holder that then tries `run heartbeat` and `intent` (refused on its `interrupted` run). The mutex between them is the `msvcrt` byte lock on Windows and `flock` on macOS; the second spelling of the record path (drive-letter case, an 8.3 name, a junction or a symlink) must still exclude across processes.
- **The clock** (finding 15): a time-sync step between two runs on a real machine.
- **What monday does with a leading-zero id** (finding 4): whether `workspaces(ids: ["040000002"])` resolves to workspace `40000002`, read-only, at the A11-1 moment in the test workspace the user names. The fix does not depend on the answer.
- **The subprocess sequence of `SubprocessTest`** under both interpreters on both systems, with `PYTHONDONTWRITEBYTECODE` set and unset, as K04 and G49 ask, after the fixes land.
