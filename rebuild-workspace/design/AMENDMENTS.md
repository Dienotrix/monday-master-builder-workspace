## A27. Show, not just tell: readiness opens with goals and pains, and the call type is a best guess (decided 2026-10-13)
Round 2 of the SPEC interview. Asked what they look for first in the readiness output, the user said goals and pains. Asked whether confirming the call type should stay a stop in the first-hour path, the user said: proceed on the best guess; "the main first goal is to show, not just tell. So even having a basic demo is better than nothing."
- **Readiness opens with goals and pains.** Part 1 of the check becomes "goals and pains": the client's stated goals in their own words, with quotes and locations, and the pains with their wanted outcomes. The `readiness/1` shape gains a `goals` list before `pains`; the 25 answer keys receive it in a small follow-up pass, and the record map's pin moves with it.
- **The call type is proposed and assumed, not confirmed.** Intake records its best guess with the signals behind it, marks it assumed, continues, and tells the user; the user may correct it at any time, and a correction re-runs what depended on it. Intake stops to ask only when it cannot tell. The same principle governs the whole first-hour path: before the approval card the plugin asks only what it cannot infer; everything else is assumed, labelled and shown on the card (A25).
- **A basic demo beats nothing.** Where the inputs are thin, the first build is a generic workspace with its assumptions listed, built and shown, rather than a wait for better inputs.
- **The hour is the floor, not the typical case (round 8 of the interview).** There are normally one to three days of preparation before the client meeting. When that time exists, the research deep dive runs before the first build, the sample data is refined, and round two, the AI layer, is built and audited before the first showing; the user sets the cadence, and the plugin proposes it from the time available. The two-round default of A27 and Q5 describes the order of work, not a rule that the AI layer waits for a showing.

## A25. Assumptions may carry a proof of concept; a working solution needs them confirmed (decided 2026-10-13)
Reading the spec against the architecture, the user found two different requirements: the readiness check expressly allows a generic proof of concept based on assumptions, while the detailed architecture says the proposed structure must be confirmed with the client before anything is built on it. In the user's words: a prospect who has only supplied a transcript might not be available to confirm the proposed structure before the first demo, and that is exactly when the builder should move forward intelligently. The rule, as the user set it:
- For a proof of concept, user-approved assumptions can support building, provided they stay visibly unconfirmed.
- For a client-approved working solution, the relevant structural assumptions must be confirmed or otherwise explicitly accepted before production use.
- An unconfirmed structural decision does not by itself prevent a proof of concept. The builder chooses a reasonable approach, explains the assumption, obtains the user's approval, and preserves that distinction for future iterations, so an assumption never turns into a fact.
- **Consequences the design takes (the assistant's reading, for the user's nod):** the client term read-back before a build becomes, when the client cannot be reached, a list of assumed terms the user approves on the card and the plugin reads back to the client at the next contact; an element at fork open, or an open structural question, is built on its leaning with the user's yes and marked assumed, the card saying what a later switch to the other option would and would not restore, and the user's blocking flag on a fork [L14] stays the one way to stop a build on that point; the version carries its purpose, proof of concept until the client signs off and working solution from v1.0, and the `signed-off` event requires every structural assumption confirmed or explicitly accepted by the client, recorded in the record; assumptions live in the record, the approval card and the build notes, never as text inside the client's workspace.
- **Answered 2026-10-14, before the fold-in: sign-off warns, it does not block.** Recording the `signed-off` event lists every structural assumption not yet confirmed or accepted by the client, and the user records the event anyway if they choose. The user: "It should warn for now."
- **Answered 2026-10-15: every version during the sales process is a functional proof of concept.** The user: "we're working through the sales process so for now, it's technically a functional POC. Once sale is closed, then we work towards real final solution." So a version's purpose follows its number: every `v0.x` is a proof of concept, and a client's sign-off of a `v0.x` leaves it one; when the user reports the sale closed, the plugin proposes opening `v1.0`, and from `v1.0` the work is the working solution (decision G23 of WP2, its default confirmed). The user added the same day: "Ideally our POCs get very close to the real solution. The only thing that holds us back is just getting more and more context from client until we get a V1. So from sales into implementation should be a smooth process." So `v1.0` is not a rebuild: it continues the same strand in the same workspaces from the last `v0.x`, as one more iteration, with the assumptions still open listed to confirm; each `v0.x` is built to be as close to the real solution as the context allows, and the gap it closes is context, not quality.
- **Answered 2026-10-14: the term read-back shrinks to what matters.** Column names and status labels are too granular to confirm. What needs confirming is the automation conditions and a general overview of the board architecture, which the user, as solution architect, normally confirms. When the client cannot be reached before a proof of concept, those are listed on the approval card marked assumed, the user's yes lets the build go ahead, and they are checked with the client at the next contact.
- **Answered 2026-10-14: the user is always the one who confirms.** The plugin never deals with the client directly. The client gives the user feedback, and the user gives it to the plugin; for a working solution as for a proof of concept, the confirmation the plugin records is the user's, reporting what the client said. In the user's words: "I confirm, but the client is the one giving me the feedback, and then me giving you the feedback."
- **Answered 2026-10-14: an open choice is built on its leaning.** A fork or an open structural question is built the way the evidence leans, with the user's yes, marked assumed; the card says what a later switch would and would not keep; the user's blocking flag [L14] stops that part. The user added: with a note in the document explaining why it is an open item until the client explains or clarifies.
- **Answered 2026-10-14: the note lives in the build notes, not in monday.** Assumptions and open items are kept in the record, on the approval card and in the build notes (A23), where each open item gets a short paragraph: what was assumed, why, and what the client needs to clarify. Nothing of it is written as text into the client's workspace. The user added a direction for later: the plugin should one day generate a master document with diagrams, explaining the solution and why, and how to use it, with SOPs. That is the v2-or-v3 client SOP and handoff package (A19), and the build notes are its seed; nothing of it is v1.
- Folded into SPEC in the interview of 2026-10-13; ARCHITECTURE and BUILD-PLAN with A24, as the first task of stage 2.

## A23. Build notes after every demo build: an internal explainer with diagrams and a presentation checklist (decided 2026-10-13)

## A18. v1 uses every monday feature the connector exposes; authored scripts are v2 (decided 2026-09-13)
The user asked whether the plugin builds on monday Workflows, not only automations, and whether it can write Python scripts when required, and stated that v1 must be able to use all of monday's features and build on them. The design's v1 exclusion list — published workflows, CRM sequences, webhooks, bulk import, notifications and updates, AI agents and AI columns — was a safety default written before this decision, not a scope the user chose.
- **Scope.** Every feature the connector exposes is in v1 scope as an element kind: boards and everything on them; automations; **monday Workflows** — created, validated, published, run once and stopped through the workflow tools, with monday's own workflow expert and process planner used as design aids and never as authorities; CRM sequences; webhooks; forms; docs; dashboards and widgets; portfolios and projects; AI agents, AI columns and Vibe apps (A17); and notifications and updates as designed outputs of a workflow or an automation, with recipients shown on the approval card. The one standing exclusion is `delete_*` in a client account — archive instead. **Narrowed 2026-10-14 by the user:** the plugin itself deletes nothing in any account, the user's own included, at least for now; removal is a by-hand step it lists. Deleting test objects is allowed only while the plugin is being developed, by the development tooling that never ships, inside the test workspace the user names (A11-1). Bulk import stays a v1 size limit (the item tools up to about 500 rows), not a scope exclusion.
- **The safety model extends rather than loosens.** Each kind gets the same path a board gets: a live probe first, a gotcha entry, an element key in the blueprint, a build step of intent → call → record → read-back → verify, an audit check, and a switch-off step in the handoff wherever the API cannot switch the thing off itself. Published workflows and sequences that reach people are approved as a list with every recipient shown, the way automations are (A1). Nothing is promised in a client-facing script until its kind has been probed on the ring in use.
- **Workflows versus automations.** Where a need can be met by either, the blueprint says which and why — a workflow for multi-step, branching or cross-board logic, an automation for a single trigger-action pair — and records, from the probes, what the API can and cannot do to each afterwards: activate, deactivate, delete, read back.
- **Scripts are v2.** Authored scripts, in Python or otherwise, hosted wherever monday can run them — a workflow code step, a Vibe app, or an integration outside monday — are designed in v2, together with HTTP and other external-call blocks inside workflows where those turn out to need authored code; a plain HTTP block that monday hosts natively is probed with the rest of the workflow blocks and belongs to v1 if the probe passes. In v1 a scripting need is recorded as a requirement with its mechanism named and left unbuilt, or routed to a Vibe app where that fits (A17). No v1 element kind carries executable code the plugin wrote. monday's own assistant (Sidekick) is probed for what the connector can configure about it; anything it exposes joins the same path.
- **Sequencing.** Workflows, sequences, webhooks and notifications join A17's stage after the current five: probes, a design pass over the architecture and the build plan, then the build. The user may pull any of it forward.

## A17. monday AI agents, AI columns and Vibe apps are element kinds, and the plugin authors their prompts (decided 2026-09-13)
The user asked that the product be able to build prompts and inject them into monday's AI agents, and build monday Vibe features, not only boards and automations. The design had excluded AI agents and AI columns from v1 as a safety default and had no element kind for Vibe apps at all.
- **Scope change.** "AI agents and AI columns" leave the v1 exclusion list, and Vibe apps join the element kinds. This narrows A13: "non-platform" now means outside monday only. An AI agent, an AI column or a Vibe app is platform work built through the connector, with an element key, a build stage, a read-back and an audit like any other element. A client's own partial Vibe prototype (the shape a scoping session produces) is a prior build to inherit and extend, never to overwrite.
- **A prompt is a design artifact, approved before it is injected.** For each agent the blueprint carries its role, its instructions, its knowledge sources, its skills, its triggers, the boards and columns it may read and may write, and what it must never do — written in the client's vocabulary from the record, leak-linted, claims-disciplined and neutral-named. The set of agents is one approval unit on the card, every row shown in full, the way the automations list is. Prompt text is versioned inside the strand like a blueprint section; a change to a live agent's prompt is a change-table row with its prior state and its own yes.
- **Vibe apps** are specified from the blueprint — purpose, the data they read, the actions they take, the boards they bind to — created and iterated through the connector's Vibe tools, and read back where those tools allow. Publication is a separate step of the irreversible class with its own yes, because it can carry a cost and makes the app visible beyond the builder.
- **Credits are not the plugin's concern.** The user decided (2026-09-13) that the plugin neither measures nor prices AI credits; selling and managing credits is the user's job. The plugin records a client's consumption question as a design input when the client raises it [L15], names which elements are AI-powered so the user can price them, and never states a credit figure, price or package.
- **Safety.** These are account-level objects: each creation asks. The guard's write matcher covers the agent, Vibe and AI-column tools; an agent's write scope is limited to the strand's build targets; agents are built last, after automations; nothing an agent can act on is enabled in a client account until it has been read back; the audit verifies prompt text, knowledge, triggers and scope against the frozen revision; the handoff records how the client switches each agent off and whether the API can do it. A prompt never carries a credential, an internal note, or anything the leak lint would refuse in a client-facing document.
- **Nothing is promised until probed.** Live probes come first, in the [A11-1] workspace, with the user's yes before any account-level creation: what each agent and Vibe tool returns, what can be read back, what can be deactivated or deleted, whether a Vibe app is visible before publication. Each finding becomes a gotcha entry, and no client-facing script may claim a capability from this family that has no entry.
- **Sequencing.** Added as a stage after the current five, so the running build is not destabilised: probes, then a design pass over the architecture and the build plan (element kinds, templates, an agent-prompt template, skill references, audit checks, fixtures and a sandbox scenario), then the build. The user may pull it forward.

## A16. Client documents are an input class alongside transcripts (decided 2026-09-12)
Sometimes the client supplies a design document instead of, or as well as, a call: SOPs, flowcharts and process maps, general guidelines, requirements write-ups, spreadsheets or exports of what they track today. These are evidence, but they are not speech, and the rules differ.
- **A document is authored, not spoken.** Record its author (if known), date, and status — draft, approved, current practice, desired state — and treat each as unknown when the document does not say. Cite by document and section or page, never by speaker. Where the author is unknown, the citation tier is "the client's document", one step below an attributed quote.
- **Documented process is not lived process.** An SOP says how things are supposed to work; a transcript often shows how they actually work. When a document and a call conflict, record both with their sources. That conflict is a finding in its own right — often the best callback material there is — and never a reason to discard either.
- **Current state versus desired state are recorded separately.** A requirements document or a "what we want" write-up feeds the requirement trace and the solution, not the current-state picture. A process document feeds current state. A single document can carry both, section by section.
- **Grading.** A document can satisfy current-state and requirements criteria. It does not satisfy the cost, why-now, decision-process or next-step criteria unless it states them explicitly, and a stated figure in a document is a client figure with the document as its source. A document-only engagement still produces a grade, with every gap the document cannot fill shown as a gap.
- **Diagrams are read, not skipped.** Flowcharts and process maps are read from the image or PDF and turned into steps and decision points in the same structure inventory the reverse-demo uses, with a third source marker — *documented* — beside *spoken* and *observed*.
- **The client's own SOP is the starting point for ours.** When the handoff SOP is produced, it reuses the client's vocabulary and structure where they have one, and shows what changed.
- **Storage and safety.** Client documents live in the record's inputs area under the same leak-lint, neutral-naming and retention rules as transcripts. The open A11 retention question covers documents as well as transcripts; it stays open.
- **Any combination, one path.** The inputs for a client are whatever arrived: one meeting alone; one meeting plus some design documents; a package of meetings and no documents; documents and no meeting yet; anything in between, arriving in any order over time. All of it goes through the same intake, into the same record, and is graded and designed together. Nothing may require a transcript to exist before a document is read, or the reverse, and nothing may treat the first input as special because it was first.
- **Added 2026-10-13, the user's decision:** emails are an input class beside transcripts and documents, because the information for a client demo may come in many shapes and sizes: an email with attachments, a forwarded thread, a message with a document pasted in. Sender, date and thread are recorded the way a document's author and date are, with unknowns left unknown, and the same one path applies.
- **Added 2026-10-14, the user:** emails will probably arrive as screenshots or as text the user copies in, not as mail files. The design takes it this way (the user's yes, 2026-10-14): pasted text is an email input handled like a document, saved unchanged, with sender, recipients, date and thread order recorded where the text shows them and `unknown` where it does not; a screenshot is saved as an image and read by the model, the way a diagram is, with its text written out beside it and cited by image and region; an attachment counts only when the user adds it as its own input. No mail-file or mailbox parsing is built.

## A15. A package of calls can arrive at once; the record digests all of them before anything is built (decided 2026-09-12)
**One call is the common case and the default.** Often the user gets exactly one meeting, and everything below must work from a single transcript with nothing else. A package is the same flow with more than one input, never a separate mode: nothing in intake, grading or the blueprint may require, assume or wait for a second call. Sometimes the user is handed a whole package by another seller or sales engineer — discovery, one or more demos, a call review, a pricing call — often from a call-recording platform whose export is yet another transcript grammar.
- **Intake takes the package as a set.** It types each call (the call-type taxonomy), orders them by date and by internal evidence rather than by filename, records who was in each, and builds **one record from all of them before grading**. A package handed over second-hand is treated as second-hand: a client figure the handing-over seller re-quotes is not fresh client evidence.
- **Cross-call conflicts are recorded, not silently resolved.** Both statements are kept with their call and speaker; "the most recent statement wins" is not the rule. Unresolved conflicts become gap questions for the next meeting.
- **Grading and the blueprint run once against the synthesized record**, so the first build is a proof of concept or v1 assembled from the whole package, not from the last call in it.
- **Afterwards, every new meeting is one more call into the same record**: a new strand version, building only the difference from the version before. "Rework what is established" covers both what the product built and what already existed in the client's account, through the blueprint's new / pre-existing-changed / pre-existing-referenced inventory and the approval a pre-existing change takes.
- Recordings and call-platform links stay out of the record (a link at most); text transcripts go in. Format detection stays measure-first, because every new source is a new export grammar.

## A14. One record per client, with strands of work inside it (decided 2026-09-12)
The record is keyed to the **client**, not to the engagement. A client who already has a live build from earlier work gets one record, and each new piece of work is a **strand** inside it.
- A strand carries its own scope, versions, blueprint, built objects and close-out. The record carries the client: research, stakeholders, the account's plan and products, the cross-strand history, and what is already live.
- **A prior live build is first-class context, not a link.** New work must be able to read what already exists, what it constrains, and what must not be broken.
- **Versioning moves to the strand.** Two strands version independently; the record shows both.
- **The build lease stays singular and is now contended.** Only one strand may hold a live build lease on the account at a time; a second strand asking for it is told which strand holds it and waits. This is a new failure mode the per-engagement design never had — treat it as a designed-for case, not an edge case.
- **Close-out becomes two-level:** a strand closes (handover, SOP, archive of that strand) while the record stays open; the record closes only when the client relationship ends, and that is what triggers the repo archive and the local-folder cleanup.
- Bloat control matters more here than before, because a record now outlives several engagements. The per-strand summary, not the raw history, is what later strands read.

## A13. Bespoke, non-platform work: record and hand off in v1 (decided 2026-09-12)
Some strands are not a platform build at all — a custom app, a script, an integration against a third-party system. v1 **records** those and **does not design or build** them.
- The product captures the strand's scope, the open technical questions, the external dependencies, the access needed and the next steps, in the same record as everything else.
- It then says plainly, in the record and to the user, that building this strand happens outside the product. No non-platform element kinds, no build stage, no audit for it.
- The gates still apply to what it does own: claims discipline, the leak lint, the approval stop on anything written into the client's account.
- Revisit after the first real engagement of this kind. Designing such work is deliberately deferred, not rejected.

## A12. No personal names in any document or in the plugin (decided 2026-09-12)
Every working document, and every file the plugin ships, refers to **"the user"** rather than a personal name, and uses they/them. The goal is that any of this can be handed to someone else without rewriting it.
- Already applied across the design, live-test and research documents (names replaced, pronouns corrected).
- The plugin's own skills, references, scripts and templates follow this from the first line written.
- Client-facing output stays neutral as before: no personal names, no brand names, nothing naming the plugin.

## A10. Chat boundaries: by unit of work, not per meeting (decided 2026-09-12)
The earlier "a new chat per meeting" rule is replaced. Chats break on work boundaries and context size:
- **Always a new chat when switching clients** (a different Cowork project and folder).
- **Start a fresh chat for heavy work:** a build, or an audit of one.
- **Otherwise keep the same chat across several meetings** (call intake, blueprint revisions, demo script) until it slows down or starts summarizing older messages.
- **The plugin nudges the user** when a fresh chat is worth starting, for example right after a version is built, so they do not have to track it.
This changes guidance only. The client record stays the memory, and every chat still starts by reading CLIENT.md, which is what makes a fresh chat cheap.

## A4. Self-refreshing monday knowledge
When the change check finds changes, **update the plugin's monday knowledge**, so it stays current instead of raising more flags as it ages:
- The knowledge overlay (the gotcha list, the read-back rules, and the roster and schema baselines) lives in a shared folder on the Mac, for example `~/DelOps/monday-knowledge/`, that every client Cowork project connects to. The plugin reads the overlay first, then its bundled defaults.
- After each check, re-baseline so the next comparison is against today.
- Changes that alter build behavior are proposed to the user for approval; cosmetic changes (new optional arguments, added tools the plugin doesn't use) are recorded automatically.
- From time to time, fold the overlay back into a plugin release. That runs in Claude Code on the Mac, which has GitHub access.

## A5. Native template boards for CRM and Service
When CRM or Service is in scope, the solution **must use the account's native template boards** (CRM: Leads, Contacts, Accounts, Deals/Opportunities, Activities, and so on; Service: Tickets and its native companions), never look-alike boards.

Three layers:
1. **Detect** (preflight, live): find the native boards with the detection rules (see `shared/native-objects.md`) and record their ids per entity in the client record. The blueprint maps CRM and Service entities to those ids.
2. **Guard** (hook): a PreToolUse hook on create_board and duplicate_board (matcher `mcp__.*__(create_board|duplicate_board)`, plus the raw write tools) blocks, or asks the user about, any board that would duplicate a native entity. Hooks can't query monday, so the hook checks tool_input against the recorded native ids and entity names.
3. **Audit** (post-build, live): verify every CRM and Service entity in the blueprint lives on its native board.

If hooks don't run in Cowork, layers 1 and 3 still enforce the rule. Test hooks in Cowork early.
