# monday Master Builder: product spec

v1 design re-cut 2026-10-13 under A1 to A28 and reviewed with the user by interview the same day; re-cut 2026-10-14 under A24 to A28 for the user's answers of that day (GitHub as an option, sign-off that warns, the narrowed term read-back, forks built on their leaning, where assumptions live), with the stage-2 consistency check of that day applied; archive simplified and development-only deletes allowed per the user's answers of 2026-10-14, and full headless suite on both systems per the user's answer of 2026-10-14; emails as pasted text or screenshots, and the goal-quote grader check, per the user's answers of 2026-10-14. Plugin `monday-master-builder`, author DelOps, in a private repository named in its manifest. The design is in `ARCHITECTURE.md`, the build order and tests in `BUILD-PLAN.md`, and the user's decisions in `AMENDMENTS.md`, which overrides the other documents wherever they conflict with it.

**The objective, in the user's words.** Take any form of information, normally transcripts, and build a monday.com proof of concept or functional demo for the potential client, across Work Management, CRM and Service, with the proper structure selected, the API reviewed as needed, the correct boards used, and built on monday's main AI offerings. Selling and the client SOP come later (A19).

## Who it is for

The user is a monday.com consultant who turns what a prospect or a client has told them into a working proof of concept, shows it, and iterates it from there. Every skill is written for "the user", so whoever installs the plugin can use it without rewording.

- **One surface, two systems.** Claude Code on the user's own machine, Windows or Mac, as used from the desktop app's Code side (A20, A24). The behaviour is identical on both: every filesystem, process, Python, archive and cleanup operation is operating-system independent or has a tested implementation per system, and neither system ever needs the other. The shell is the system's own, so the record, the scripts and the home folder are all reachable, and the archive runs wherever the user is. Cowork and chat-side Projects return later, when a Project can reach the user's machine; because the record is plain files, nothing in v1 relies on something only one system has.
- **The home folder.** A generic default, `monday-builder` under the user's home directory on either system, which the plugin creates itself and the `MMB_HOME` variable overrides (D11, A24, A26). Under it: `clients/` with one subfolder per client, `cards/`, a hashed `clients-index.json` the leak lint's wall reads, `monday-knowledge/` for the self-refreshing overlay (A4), `sandbox/` for sandbox probes, `archive/`, the holding folder that keeps each closed client folder, moved there and verified against its manifest, and `local/`, which holds this user's own values: `settings.json` (the firm name and its renderings for the leak list, the default account to build in, and optionally the operational workspaces that are never on a shared screen), the sandbox account list and per-user leak terms. A GitHub account is stored there only when the user picks the GitHub archive; the default local archive needs none. Nothing of the user's lives in the plugin folder, and no account id lives in a shipped file.
- **The first-run walkthrough** (D12, A22, A26) asks two questions, the firm name with its renderings and the default account to build in, and offers two optional ones: the operational workspaces never shown on a shared screen, and whether to archive to a local folder, the default, or to a GitHub repository. It creates the tree, writes `local/settings.json`, checks Python and the monday connector on the system it runs on, warns when a `CLAUDE.md` sits above the clients folder, because a session opened under it would inherit those instructions, and explains the two doors. It checks the GitHub tool and stores a GitHub account only when the user picks GitHub. It runs once, and again on request.
- **Sessions** (D20). A session is opened in the client's folder: a new session when switching clients, a fresh one for a build or an audit, otherwise the same session across several meetings, with a nudge from the plugin when a fresh one is worth starting; the nudge is a suggestion, and the user decides. On this surface the client folder is organisation, not a wall: the shell can read the whole home, so the leak lint is what keeps one client's details out of another's build (A20).

## What it does

The plugin keeps one self-contained record folder per client under `clients/`; each piece of work for that client is a **strand** inside it, with its own versions and close-out (A14). The record is the memory between sessions: every session starts by reading it, gives a short briefing (interrupted work first), and names the next step.

- **Intake of any mix.** One call, a package of calls, client documents, an email as pasted text or a screenshot, or any combination arriving in any order, all through one path into one record (A15, A16, Q7). A transcript is saved unchanged and measured before it is read; the call type is proposed as a best guess, recorded as assumed with the signals behind it, and intake carries on and tells the user, who may correct it at any time, a correction re-running what depended on it; intake stops to ask only when it cannot tell (A27). In v1 the type's job is routing and telling the user's side's framing from the client's words (D3). The summary carries verbatim quotes at their locations; a document is cited by document and section; an email is pasted text handled like a document and cited by message and paragraph, or a screenshot read the way a diagram is, its text written out beside it and cited by image and region, with whatever the text or image does not show left `unknown`, and an attachment counts only when the user adds it as its own input; a package is ordered by date and internal evidence; both sides of any conflict are kept.
- **The build-readiness check** replaces sales grading (A19, D1). It answers one question: does the record hold enough to build a proof of concept worth showing, and if not, what exactly would close the gap. It never asks whether the client is ready to buy. From the record it writes nine parts: goals and pains, the client's goals in their own words with quotes and locations and each pain with its wanted outcome; entities and what moves independently of what; product and structure with its leanings; what already exists; assumptions; needs the build does not meet; AI opportunities; the clearance; and at most five questions for the next contact, each routed to the role that can answer it (A27). The clearance is `cleared to build`, `cleared to build, generic` or `not yet` (D2). Thin input never blocks; it widens the assumptions list and makes the first build more generic, because a basic demo beats nothing, and assumptions the user approves may carry a proof of concept as long as they stay visibly unconfirmed (A25, A27). The check is re-run after every new input.
- **The blueprint** reads what already exists first, chooses the product or products, reuses native CRM and Service boards (A5) and defaults to a portfolio for Enterprise Work Management (A6), then traces every pain to an element. Its requirement trace carries an **AI opportunities** subsection: each suggestion tied to one pain or stated need and one element kind, with its round and the probe finding it rests on, or marked unprobed (D19). Its binding section carries the **workspace plan**: one brand-new workspace per client and per product, with cross-product links as automations or workflows (A21, Q9). Automations, workflows, sequences and agents are listed with every row shown in full, including every recipient (A1, A17, A18). The terms confirmed before a build are the automation conditions and a general overview of the board architecture, which the user confirms as solution architect; column names and status labels are not confirmed separately and show on the card for the user to check. Where the client cannot be reached before a proof of concept, those automation conditions and the board overview go on the card marked assumed, the user's yes lets the build go ahead, and they are checked with the client at the next contact; an element at an open fork, or an open structural question, is built on its leaning with the user's yes and marked assumed, the card saying what a later switch would and would not keep, the build notes carrying a short paragraph on why it is open, and the user's blocking flag on a fork stays the one way to stop a build on that point (A25).
- **One approval card.** It opens with "what this build rests on", the assumptions the build fills by guesswork, the assumed terms and the forks built on their leaning, so approving the structure is also the user's yes to them, and they stay marked assumed until the user confirms them, passing on what the client said; the plugin never deals with the client (readiness spec section 8, A25). Then the elements, the lists, the irreversible steps, the UI steps with owners and the call estimate. On a proof of concept in the user's own account, where notifications reach only the user, one yes covers the whole revision, lists and irreversible steps included; in a client's account, and for any list whose rows notify real people, each list takes its own yes and the irreversible steps are confirmed again at execution (A28). The approved revision is frozen with a checksum; later edits become the next revision.
- **The build**, under one command the user types themselves. The target is a per-client choice recorded at setup: the user's own account by default, and an existing customer's own account when the work is for them (A21). Every build goes into brand-new workspaces for that client, one per product, unless it continues workspaces already built for the same client. The plugin never writes into any other workspace, and an account-level object such as an AI agent may read and write only that client's workspaces. Every write is read back. Sample rows go for realism over the hour: dozens per board where dashboards and roll-ups need real numbers, a handful where a board only has to read well; names and figures may be invented as long as they are plausible in the client's industry as the call and the brief describe it, minus the exclusion list, and every sample value is marked as sample in the record so none is ever cited as a fact (A28).
- **The independent audit**, under a second command, checks the build in a context that did not build it, proves it wrote nothing itself, and ends with `cleared to show` or `not cleared to show` (D2). On `cleared to show` it writes the **build notes** (A23), an internal explainer for the consultant: what was built, why, the trace from each pain to its elements, the assumptions to confirm, a board-logic diagram and a process map, and a presentation checklist of what to show and explain, which also lists the views the API cannot create, Kanban, Gantt, calendar, timeline, chart and workload, with their board and settings, for the user to add in monday when they choose, as a Markdown file and a browser page in the version folder. The user records when a version was shown.
- **Round two is the AI layer by default** (D4, Q5): a new version with its own card, build and audit, carrying the workflows, agents, AI columns, Vibe apps and sequences the blueprint proposed. It is round one when the client asked for AI or workflows, and the two rounds describe the order of work, not a wait: with the usual one to three days of preparation, round two is built and audited before the first showing (A27).
- **Iterate or build fresh.** Each later call is one more input into the same record; the next version builds only the difference. When a follow-up arrives the plugin proposes iterate or fresh, with its reason, and the user confirms; it never starts fresh workspaces on its own (A21). A completely different direction means fresh workspaces, with the old ones kept and archived later, as a separate step on the user's yes (Q13).
- **Versions carry their purpose.** A version is a proof of concept until the client signs off and a working solution from `v1.0`, which needs its structural assumptions confirmed or explicitly accepted, as the user reports from the client. Recording `signed-off` warns, listing every structural assumption not yet confirmed or accepted, and the user may record it anyway; it does not block. An assumption never turns into a fact (A25).
- **Research** runs through one agent in two modes: a quick brief before the first build when time allows, and a deep dive that feeds round two and the sample data, run before the first build when the usual one to three days exist and after round one when they do not (D14, Q2, Q14, A27).
- **Non-platform work**, meaning work outside monday, is recorded with its scope, open questions, dependencies and access needs, and handed off (A13 as narrowed by A17).
- **Close-out is two-level.** A strand closes with its ownership and switch-off steps recorded; the record closes only when the relationship ends, with a client card and, by default, a local archive: a checksum manifest of every file is written, and on the user's yes the client folder moves from `clients/` into `archive/<slug>/` under the home and is verified against the manifest; there is no second copy, `archive/` is the holding folder, and the user deletes from it by hand on either system; no git at runtime, no Trash or Recycle Bin. A user who picked the GitHub archive at the walkthrough gets a private repository and the clone-and-verify close-out as well, and the local move into `archive/` still happens (D15, A24, A26).

## Lifecycle

1. **New client.** The user opens a session in a new folder under `clients/`. The plugin creates the record and its first strand, records the build target (the user's own account by default; an existing customer's own account when the work is for them, A21), binds the account the user confirms, notes what is already live there, and drafts an access checklist for the client's admin when the target is a client account. Later work for the same client is another strand in the same record.
2. **Intake.** Whatever arrived, saved unchanged, measured, its call type proposed as a best guess and recorded as assumed with its signals where it is a call (A27), summarised with verbatim quotes, and merged into one record. Commitments, reactions and change requests are recorded; an exclusion list holds anything the client said must not appear in the demo (Q14).
3. **Readiness.** The check writes `readiness.md`, opening with goals and pains, and its clearance. Thin input is `cleared to build, generic`, with the assumptions listed, because a basic demo beats nothing (A27, A25); `not yet` stops the blueprint unless the user overrides with a reason, which is logged and kept visible on the strand (D1).
4. **Research, quick mode.** A short brief on the client's company, when time allows, so the sample rows read like their world. Each point is an external fact with a dated source or an inference with its basis.
5. **Blueprint.** As above: what exists, product and structure, the trace from pains to elements, AI opportunities, the workspace plan, the lists, the irreversible steps, the UI steps with owners, the plan and quota fit read live from the account, and the assumed automation conditions, board overview and fork leanings the build rests on, each fork with what a later switch would and would not keep (A25). A non-platform strand gets a scope file instead, and stops there.
6. **Approval stop.** One card, one named revision, frozen with a checksum. On a proof of concept in the user's own account, one yes covers the whole revision, lists and irreversible steps included; in a client's account, and for any list whose rows notify real people, each list is approved once, as a whole list (A28).
7. **Build, round one.** `/account-build 001/v0.1`. The build takes the record's own lock, then, before its first write, asks whether another build is running anywhere and logs the answer (D10). Then the change check (A3), preflight, the account check and the workspace scope, and the build in dependency order with a read-back after every write and the ledger updated each time. In a client's account, irreversible steps are confirmed again at execution and each list once before its first row is created; on an own-account proof of concept the card's yes already covers both (A28). Round one is the workspace itself: boards with their views, dashboards, forms, working automations, docs, and sample rows drawn from the call and the brief minus the exclusion list, dozens per board where dashboards and roll-ups need real numbers, plausible invented names and figures allowed and every value marked as sample (Q16, A28).
8. **Audit.** `/solution-audit 001/v0.1`, read-only, in a context that did not build, with before-and-after snapshots; it re-reads what earlier strands marked protected and lists what the user must check by eye. It ends `cleared to show` or `not cleared to show`, and on `cleared to show` writes the build notes (A23). The user shows the build with the notes' checklist in hand and records `shown`.
9. **Research, deep mode, and round two.** The deep dive runs before the first build when the usual one to three days exist, otherwise after round one (A27). Round two, `v0.2`, is the AI layer: workflows, agents with authored prompts, AI columns, Vibe apps and sequences, each from the blueprint's AI opportunities, with its own card, build and audit, before the first showing when time allows. Agents are built last. In a client's account a workflow's publication, an agent's activation and a Vibe app's publication are each their own yes; on an own-account proof of concept the card's yes covers them (A28).
10. **Iterations.** Each later call or document is one more input; readiness is re-run; the plugin proposes iterate or fresh with its reason and the user confirms (A21); the next version builds only the difference, whether to something the plugin built or to something that already existed. A different direction starts fresh workspaces, with the old ones kept until the user says otherwise.
11. **Versions, per strand** (D21). `v0.1` is the first proof of concept, `v0.2` the AI layer by default, later `v0.x` the iterations; `shown` and `signed-off` are events the user records, and `v1.0` means the client has signed off the build as their working system. Every version carries its purpose, proof of concept until sign-off and working solution from `v1.0`; recording `signed-off` warns, listing every structural assumption the user has not yet confirmed or accepted on the client's word, and does not block (A25). After either event the plugin proposes a release, which condenses the strand under a plan the user approves in one yes and writes the summary later strands read. A new strand starts at its own `v0.1` with the live map as context.
12. **Close-out, two-level.** A strand closes when its work is handed over: ownership and the switch-off step for every automation, workflow and agent recorded in `close-out.md`, its summary written, what it built marked live with what must not change. The record closes only when the relationship ends: a one-page client card, a local archive made by writing a checksum manifest of every file and, only after the user confirms, moving the client folder from `clients/` into `archive/<slug>/` under the home and verifying the moved folder against the manifest, with no second copy; the user deletes from `archive/` by hand on either system, and no git, Trash or Recycle Bin is involved. Where the user picked the GitHub archive, the close-out pushes to a private repository and verifies a clone as well, and the local move into `archive/` still happens (A24, A26). Only the record close archives or cleans up.

**The first hour is the floor.** From a single transcript, the path is intake, readiness, blueprint, one approval stop and the round-one build, and the aim is a whole workspace with sample rows, approved and audited, within about an hour (Q2, Q3). The hour is a floor, not a ceiling: it is measured on the test workspace, with the per-element read-back inside it, and recorded with the figure; when realism takes longer, more sample rows where the dashboards need them, realism wins (A27, A28).

**The usual case is one to three days** of preparation before the client meeting. In that time the deep research runs before the first build, the sample data is refined, and round two, the AI layer, is built and audited before the first showing. The plugin proposes the cadence from the time available and the user decides (A27).

## v1 scope

**In scope**

- monday **Work Management**, **CRM** and **Service**, at the same depth: native board detection and reuse, blueprint, build and audit (A7). Portfolios and projects for Work Management.
- Every element kind the connector exposes (A17, A18): boards and everything on them; automations; monday **Workflows**, created, validated, published, run once and stopped; **AI agents** with authored prompts; **AI columns**; **Vibe apps**; CRM **sequences**; **webhooks**; forms; **docs** written from blueprint text (D16); dashboards and widgets; portfolios and projects; and notifications and updates as designed outputs of a workflow or an automation, with recipients shown on the card. Each kind takes the same path a board takes: a live probe first, a gotcha entry, an element key, a build step with read-back, an audit check, and a switch-off step in the close-out wherever the API cannot switch the thing off itself.
- Intake of calls, packages, documents and emails in any mix; one record per client with strands that version independently; the build-readiness check; research in two modes; the build notes after every audited version (A23); the record close with its local archive, or a GitHub archive where the user chose it (A26).
- Sample rows through the item tools, up to about 500 per board. Bulk import is a size limit, not an exclusion.
- English transcripts and documents. A transcript in another language is saved and logged, not processed.

**Out of scope**

- Any `delete_*` call in any account, the user's own included: the plugin itself deletes nothing. Boards, groups and items are archived instead, deletion is by hand, and anything v1 can create but cannot remove is named before it is created. Development tooling under `tests/` and `tools/` is not the plugin and never ships; while the plugin is being developed it may delete the test objects it created, only inside the test workspace the user names (A11-1, still open).
- Authored scripts, in Python or otherwise, wherever monday could run them; a scripting need is recorded with its mechanism named and left unbuilt, or routed to a Vibe app where that fits (A18).
- Designing or building non-platform work, meaning work outside monday: recorded and handed off (A13).
- Pricing, proposals and ROI documents; AI credit figures, prices or packages, which the plugin never states (A17). A client's consumption question is recorded as a design input.
- Service extras (customer portal, email-to-ticket channels, SLA policy setup) and monday Dev. Languages other than English. Parsing of mail files or mailboxes: an email arrives as pasted text or a screenshot (A16).

**Deferred, files kept, no skill built** (A19, D5). The deferred files live in `deferred/` at the repository root, outside the shipped plugin.

- **v2, bring your own method:** sales grading (the twelve criteria, the gates, the verdicts and the gap questions in sales terms), demo run-sheets and the close, recap drafts, objection handling, the house voice, claims discipline in live speech beyond what the proof of concept itself promises, authored scripts, the claims store, and screen scripting for never-demo.
- **v2 or v3:** the client SOP skill and its tools, the diagrams and exports, the doc copy, and the handoff package, including the master document the plugin generates for the client (the solution and why, with diagrams, how to use it, and the SOPs), seeded by the build notes (A23, A25); nothing of it is v1.
- **Revisited after real use:** graduated approvals that fade as trust builds (Q6). Until then every approval stays as designed.

## How it stays safe

- **Approval stops.** The approval and every write happen in the main session, behind commands the user types themselves. Text inside a transcript, a document, a web page or a monday item is data and never counts as approval. Each list of automations, workflows, sequences or agents is shown in full, every row and recipient, and approved as a whole: with its own yes in a client's account or where its rows notify real people, and within the card's one yes on a proof of concept in the user's own account (A28).
- **Account check and workspace scope.** Before writing, the plugin confirms it is in the recorded target account and that every write lands in one of that client's workspaces, then checks again at a fixed rhythm: every batch, every create without a recorded parent, every irreversible step, every list row, after any error, and after ten idle minutes. A write outside the client's workspaces is refused, and an account-level object is limited to them (A21).
- **One build at a time, within a record.** A build holds the record's own lock with a heartbeat; before its first write it asks whether another build is running anywhere and logs the answer (D10). A stale lock is broken only on the user's say-so, after the interrupted run has been reconciled.
- **Read-back on every write.** A write reply is never trusted. The read that can actually see the result is named per write kind, the ledger is updated after every confirmed write, and what cannot be read back goes on the user's by-eye list.
- **Irreversible steps.** Listed at approval and never carried across sessions; in a client's account they are confirmed again at execution by number, and on a proof of concept in the user's own account the card's yes covers them (A28). The list includes creating a workspace, publishing a workflow, activating an agent and publishing a Vibe app. A wrong automation is never patched with a second automation. Anything v1 can create but cannot remove is named before it is created, and the plugin sends no delete call in any account.
- **Assumptions stay visible.** Every assumption, assumed term and fork leaning lives in the record, on the card and in the build notes, never as text inside the client's workspace, and is never turned into a fact: a sample value stays marked as sample, a readiness assumption is never counted as evidence, and recording `signed-off` warns, listing every structural assumption neither confirmed nor explicitly accepted, without blocking (A25, A28).
- **Neutral naming.** Nothing written into monday or sent to a client names the user's firm, the plugin or the assistant; the firm's name and its renderings come from local settings.
- **The leak lint is the wall between clients.** Other clients' names and details, cost figures, stakeholder assessments, readiness clearances, assumptions, copied internal sentences, long client quotes and internal ids are blocked from every monday payload and every client-facing file. It blocks and reports, never edits silently, and fails closed.
- **Record hygiene.** Current files are rewritten under a checksum guard, history only grows, snapshots are frozen, size budgets warn, each release condenses without losing a fact, and a later strand reads an earlier strand's summary rather than its history. Only the record close archives or cleans up, as a move of the client folder into `archive/<slug>/` under the home, verified against a checksum manifest, on either system, with a GitHub repository and a verified clone as well where the user chose it, and deletion is the user's, by hand (A24, A26).
- **Never-demo, by workspace.** The user's operational workspaces, when named in local settings, are never on a shared screen; the briefing names them whenever a version is audited (D22). A client's proof-of-concept workspace in the same account may be shown.
- **Nothing unverified is built or promised.** Every element kind is probed on the ring in use before it is promised, each finding becomes a gotcha entry, the blueprint marks an unprobed kind as unprobed, and monday's own workflow expert and process planner are design aids, never evidence. A capability with no entry is not claimed.

## A day with one client

Brackenholt Architects is fictional (fixtures s1 and s3). It is a new prospect, so the build target recorded at setup is the user's own account.

**Tuesday 9:10.** The user opens a session in a new folder under `clients/` and pastes yesterday's call: "First call with Brackenholt, here is the transcript." The plugin creates the record and strand `001-pursuits`, saves the transcript unchanged, measures it, and proposes the call type as a best guess, a first discovery call, from the signals in the opening minutes, records it as assumed and carries on; the user lets it stand. The summary carries the quotes at their locations: pursuits tracked in a spreadsheet nobody trusts, go or no-go decisions made by email, fee proposals that go stale when the scope moves. The managing partner asked that no real client names appear in anything shown, so the exclusion list starts with that.

**9:25, readiness.** Goals and pains first: two goals in the partners' own words, every pursuit visible in one place and no fee proposal going stale unnoticed, then three pains, each with an entity and a wanted outcome. ## What the live testing changed

Live testing in a real monday account recorded 90 behaviours of boards, automations, views and native objects, and a later set of probes covered three of the AI kinds. Several findings trimmed what the plugin promises down to what the API can actually back up.

- **Dashboards are built, not verified.** No API call can read a widget back, so the plugin creates a dashboard and then puts it on the user's by-eye list. It never claims the widgets show the right numbers.
- **Automations are one-way.** One made through the API cannot be switched off through the API, even by the person who created it. So the approved list says so up front, and every automation carries a "turn it off in monday" step in the close-out.
- **Some views have to be made by hand.** The view enum was re-checked on the live schema on 2026-10-13 and still holds four creatable kinds, table, dashboard, form and app, the last needing an app feature id. Kanban, calendar, Gantt, timeline, chart and workload views cannot be created through the API or the connector, so they stay hand-made: UI steps with a named owner, listed in the build notes' presentation checklist with their board and settings for the user to add when they choose (A23). A probe is noted for the test workspace on whether the app kind, given a built-in view's feature id, creates one of them, and the change check re-reads the enum at every build so a kind monday adds is picked up.
- **Native CRM and Service boards are protected by id.** Nothing in the API marks a board as native, so the plugin records the real board ids and their template lineage at preflight and guards those, never a board's name or its columns, both of which anyone can edit or imitate.
- **Agents.** The plan round-trips verbatim, but only through a read: the reply to an update reported the plan empty while a later get returned it in full, so a read-back is the only proof that the approved text was injected. An update can activate an agent that was created inactive, so every update is followed by a state read and a deactivation when it should be off. Every new agent arrives with two default triggers it was never asked for; the blueprint lists them and the audit expects them.
- **Vibe apps.** Generation is asynchronous and is polled, and the generator can reinterpret the spec, so the audit's main job is a diff between the delivered app and the request. Code versions and the build conversation are readable. Delete removes the app and its board view, but v1 sends no delete call in any account, so removing a Vibe app stays a by-hand step named in the close-out.
- **Workflows.** Publication is one-shot per draft: publishing consumes the draft, and no tool in the roster activates a workflow that was published inactive, so the activate-or-not choice is made at publication: its own yes in a client's account, and covered by the card's yes on an own-account proof of concept (A28). monday's workflow expert is a design aid and never evidence: its error messages and its success messages have both disagreed with the live state, and only a read of the draft or the published object counts.

## Open decisions

Three decisions are open (A11), and no default is assumed for any of them. The plugin marks each one open and asks the user at the moment it first matters, once per client where the decision is client-specific, which may be during a later strand, and never at new-client setup.

- **Where write probes and test scenarios run** (A11-1). No live writes until the user names a test workspace, which they do when the first live probe asks, and no long-term answer is assumed. The probes that wait on it are listed in the stage 1b plan: whether creating a CRM or Service workspace installs the native boards, whether an automation or workflow can act across two product workspaces, whether an agent can be limited to named workspaces, a formula result landing in a date column, an AI column write, a sequence, and a webhook.
- **Sample data inside a live client account** (A11-2, scoped by A21). Sample rows in the user's own account need no decision. Sample data inside a client's own account is asked before the first such build, and none has happened yet.
- **Transcript redaction and retention** (A11-3). Asked before the first real client transcript, document or email is saved. Only fictional fixtures exist so far.

Everything else that shapes the build has either an answer from the user or a default that ships; those are recorded in `ARCHITECTURE.md` section 12, and the platform and monday items still to be probed are listed beside them.
